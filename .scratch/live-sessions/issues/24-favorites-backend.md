# 24: 收藏的後端：查收藏的 session、依 id 接續、判斷接續不了

**What to build:** 讓收藏超過 24 小時的 session 也查得到、接續得了。前端把收藏的 `agent:id` 交給 `GET /api/live`，後端回傳每一筆的資料與狀態（還開著、已結束、接續不了），並把收藏從「最近結束」排除、不佔 10 筆名額。`POST /api/live/resume` 改成依 id 查已結束的 session，不再限於「最近結束」清單。

使用者 2026-11-18 選定需求與技術做法（grilling 四輪）：T1 A、T2 A、T4 A；T3 為實作細節。細節見規格的「實作決策 → 收藏」。

## 技術做法（已核准，建議選項即定案）

### T1：前端怎麼把收藏交給後端

- **A（建議）**：`GET /api/live?favorites=claude:<id>,codex:<id>`，回傳多一份 `favorites` 清單。每 3 秒的輪詢一次拿齊三份清單，後端順便從「最近結束」排除收藏。id 必須通過 UUID 檢查，最多收 50 筆，不合格的略過。沿用既有的 Host 檢查，不新增寫入端點。
- B：另開 `POST /api/live/favorites` 查收藏。要多一支端點，而且排除「最近結束」時要靠前端合併兩份回應。

### T2：「接續」怎麼認得收藏的 session

- **A（建議）**：`post_resume` 改成依 id 直接查已結束的 session，不限 24 小時：Claude Code 找 `projects/*/<id>.jsonl`，Codex 查狀態資料庫。仍然要求 UUID 格式、資料夾由伺服器自己查、還開著的拒絕。
  - 安全上的改變：原本只能接續「最近結束」的 10 筆，改成這台電腦上任何還留著紀錄的 session。仍然只接受看板自己頁面的 POST（Origin 檢查），指令仍然只有兩種固定形式，所以風險不變。
- B：請求另外帶「這是收藏」，伺服器才放寬限制。這個欄位由前端自己宣稱，擋不了什麼，只是多一個欄位。

### T3：怎麼判斷「接續不了」

每筆收藏回傳 `state`：

- `open`：還開著，附上與「進行中」相同的 id，前端點了跳轉。
- `ended`：已結束，可以接續，附上名稱、資料夾、最後活動時間。
- `gone`：確定接續不了，附上原因：
  - 對話紀錄不存在：Claude Code 在 `projects/*/` 找不到 `<id>.jsonl`；Codex 的狀態資料庫沒有這段對話，或它的紀錄檔不在了。
  - 資料夾不存在：紀錄裡的工作資料夾已經被刪掉。
- `unknown`：讀取出錯，例如 `projects` 資料夾讀不到、Codex 資料庫開不了。前端不移除，照常顯示上一次拿到的資料。

前端只在 `gone` 時移除。

### T4：Claude Code 清除紀錄前的提醒

先前同意的是「超過 30 天提示『對話紀錄可能已被清除』」。但 Q12 選了自動移除，紀錄真的被清掉後，那筆收藏會直接消失，這個提示就看不到了。所以改成提前提醒：

- **A（建議）**：從 Claude Code 的設定讀保留期限（`~/.claude/settings.json` 的 `cleanupPeriodDays`，沒有就用預設 30 天），最後活動超過「期限減 7 天」時提示「約 N 天後可能被 Claude Code 清除」。只讀設定，不修改。Codex 不會自動清除紀錄，所以不提示。
- B：照原本的寫法，固定超過 30 天才提示，不讀設定。
